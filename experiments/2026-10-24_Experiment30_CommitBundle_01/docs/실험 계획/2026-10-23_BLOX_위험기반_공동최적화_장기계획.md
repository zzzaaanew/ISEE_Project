## 1. 장기 연구 질문과 완료 기준

> 동일 ML 위험 Parquet을 필수 입력으로 사용하는 위험도 ON 상태에서, 5분마다 Job Queue의 실행 작업 선택과 GPU Placement를 공동 최적화하면, 같은 위험 입력을 쓰는 FIFO·Tiresias-style 기준선보다 작업 지연과 연산 손실을 개선할 수 있는가?

- 단순 ON/OFF 비교나 취약도 가중 위험 합 감소를 최종 기여로 삼지 않는다. E26·E27 OFF 결과는 역사적 근거로 보존하고 앞으로의 주 비교에 OFF를 자동 추가하지 않는다.
- 논문 수준의 목표는 목적함수·변수·제약·정보 경계가 명시되고, 구현 충실도·해의 품질·실제 운영 지표·불확실성·한계를 함께 검증한 온라인 최적화다. 특정 solver 사용만으로 이 기준을 충족한 것으로 보지 않는다.
- 같은 기간을 보고 설계한 retrospective 결과와 새 미관측 기간의 일반화 검증을 구분한다. 현 E19/E27 기간은 개발·방법 검증에 사용된 기간이다.
- 최종 완료는 사전 고정한 주 지표 개선과 공정성/잔여 작업량 가드, 정확성·계산 예산 검증, 시간순/외부 검증이 충족될 때 판단한다. 승리 수치나 개선율을 미리 약속하지 않는다.

## 4. Baseline 정의와 구현 충실도

| ID | Queue·실행 선택 | Placement | 위험 사용 | 해석 |
|---|---|---|---|---|
| B0 | 제출순 FIFO | 공통 risk-aware packing | 같은 Parquet의 위험으로 배정 후보 비교 | FIFO 기반 ON 기준선 |
| B1 | Tiresias-style Discretized 2D-LAS, 큐 내부 최초 실행순 FIFO, 기아 방지 | B0와 같은 risk-aware packing | B0와 동일 | 원형 Tiresias 전체 재현이 아닌 명시적 결합 기준선 |
| P | 실행 작업 선택·유지/선점·GPU 집합을 함께 결정 | 공동 최적화 | 같은 Parquet에서 파생한 공통 위험 입력 | 검증할 제안 구조 |

- LAS는 실행 우선순위 규칙이다. 이를 물리적 GPU 위치 결정 규칙과 같은 계층으로 적지 않는다.
- FIFO는 두 의미를 구분한다. B0는 **제출순**, B1 동일 큐 안에서는 **최초 실행순**이다. 제출순 FIFO+backfill을 쓰면 strict FIFO와 별도 이름으로 보고한다. HOL 차단/skip 규칙은 구현 승인 계약에서 명시하며 암묵적으로 바꾸지 않는다.
- 현 `NativeScheduler(..., name='Tiresias2Q')`는 간이 어댑터이며 논문 전체 구현이 아니다. 원문 기준 서비스량·queue 전이·동률 처리·기아 방지 검사를 통과하기 전에는 논문 원형 결과로 표시하지 않는다.
- 모든 arm은 비용·사건 처리·정보 접근·판단 주기·공통 lease/전환 회계 경계를 공유한다. lease 유지가 가능한데도 매 라운드 무조건 checkpoint/restart를 부과하지 않는다.
- B1을 공통 위험 배정/lease와 결합하면 정확한 명칭은 Tiresias-style 기준선이다. 논문 원형과 달라진 부분을 manifest·요구사항 매트릭스에 기록한다.

## 5. 공동 최적화의 수학적 계약 초안

### 5.1 결정 변수

- `y[j,k] ∈ {0,1}`: 계획 슬롯k에서 작업j를 실행할지.
- `x[j,g,k] ∈ {0,1}`: 작업j를 GPUg에 배정할지.
- `z[j,k] ∈ {0,1}`: 해당 슬롯에서 비용을 발생시키는 중단/배정 변경이 있는지. 단순 계획 재계산은 z=1의 근거가 아니다.
- 대기·실행·복구·완료·정비 상태와 유효 progress는 별도 상태 전이로 추적한다. solver에 쓰는 예상 소요시간과 시뮬레이터 환경의 실제 trace duration을 분리한다.

### 5.2 목적 후보

`min E[Σ_j w[j] × (completion[j] − arrival[j])]`.

- 작업 지연 초를 기준으로 비교 가능한 주 목적 후보다. `w[j]=1`은 동일 작업 가중 후보이며 GPU-초와 임의 혼합하지 않는다.
- 오류 rollback·복구·checkpoint·선점이 완료시각을 늦추는 상태 전이에 이미 들어갔다면 같은 지연을 별도 penalty로 다시 더하지 않는다.
- 온라인 실행은 유한 구간을 계획하고 첫 행동만 실행하는 rolling/receding-horizon 방식 후보를 사용한다. 한 구간의 해를 전체 온라인 전역 최적해라고 하지 않는다.
- 미완료 작업이 많은 현 workload에서는 완료 작업 평균만 최소화하지 않는다. 유한 구간 내 미완료 작업의 체류시간과 terminal 잔여 작업량/가치를 포함하는 명세가 필요하다. 수치형 terminal weight는 미확정이다.
- 위험 score가 확률로 보정되지 않은 상태에서 위 기대값을 실제 기대손실이라고 주장하지 않는다. 보정 전 실험은 surrogate/가정 조건부 실험으로 명시한다.

### 5.3 자원·운영 제약 후보

| 제약 | 기본 관계·의미 | 확정/검증할 부분 |
|---|---|---|
| GPU 중복 방지 | `Σ_j x[j,g,k] ≤ available[g,k]` | 정비·실패·quarantine 상태와 일치 |
| Gang 원자 배정 | `Σ_g x[j,g,k] = demand[j] × y[j,k]` | 부분 Gang 실행 금지 |
| 준비 상태 | 미도착·완료·복구 중 작업 실행 금지 | 360초 복구처럼 슬롯을 넘기는 지연을 반올림해 없애지 않음 |
| 변경 비용 | z는 실제 중단/배정 변경에만 연결 | 동일 작업·동일 GPU 집합 lease 갱신은 재시작 없음 |
| lease/선점 예산 | 최소 유지·선점 횟수·비용 예산 후보 | 실제 고장/강제 복구 예외와 기아 방지를 함께 검증 |
| 공정성 | aging·대기/서비스 보호 후보 | 과부하에서도 가능한지 확인. 불가능한 hard 최대대기를 선언하지 않음 |
| topology | 서버/GPU 배치 제약·통신 효과 | 서버 penalty의 단위를 측정 성능과 연결하거나 별도 구조 가정으로 표시 |
| 계산 예산 | 300초보다 짧은 solver 시간 제한·fallback | 후보 집합 크기·time limit·gap·fallback 횟수를 기록 |

- 미래 XID·미래 도착·향후 실제 완료시간은 정책에 전달하지 않는다. trace는 환경의 사건 발생과 사후 평가에만 사용한다.
- 위 `available[g,k]`는 고장·정비 등을 제외한 물리적 사용 가능성이다. 현재 실행 중이라는 이유만으로0으로 두면 기존 배정 유지가 불가능해지므로, 현재 점유는 기존/새 작업의x와변경상태로 일관되게 처리한다.
- 과거 완결 작업 기반 duration 추정이 준비되기 전에는 oracle duration 조건을 분리해 표시한다. 기존 oracle 비교만으로 배포 가능한 정책을 입증하지 않는다.
- GPU 이동으로 회피 가능한 오류와 작업을 따라가는 앱 오류를 구분한다. Job/PID 연결이 없는 GPU-local 앱 사건은 민감도 가정으로 남긴다.

## 6. 선점 비용과 오류 손실의 불균형에 대한 원칙

- 두 비용을 같은 크기로 만들기 위해 오류 penalty·하드웨어 비율·복구시간을 임의 증가시키지 않는다.
- 5분마다 평가하되 이전 배정을 유지하는 선택을 허용한다. 우선순위 이산화·큐 내부FIFO·lease renewal은 재선점을 억제하는 근거 기반 후보다.
- 예방 행동은 `기대 이득 > 전환 비용 + 유발한 큐 지연 + 불확실성 여유`를 만족해야 한다. 이는 연구 설계 원칙이며 현 코드에 구현돼 있다고 주장하지 않는다.
- 현재 R0의660초는 세션 간격 대조값이다. 선점60+300초와 의미가 다르며 정상연산 재개시간 전체/유형별 실측 분포로 쓰지 않는다.
- 현재 periodic checkpoint 저장은 정지 비용을 부과하지 않는다. 논문용 공통 비용 모델에서는 이 비대칭을 해결하거나 가정별 민감도로 분리해야 한다. 비용 모델 변경을 P에만 적용하지 않는다.
- 판단 주기·risk 원정보 갱신·checkpoint 주기는 서로 다른 축이다. checkpoint를 무조건5분으로 고정하거나 24시간p를 단순288분할하지 않는다.
