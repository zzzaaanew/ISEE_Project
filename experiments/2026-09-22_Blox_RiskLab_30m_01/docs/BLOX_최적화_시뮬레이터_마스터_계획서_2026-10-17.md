## 1. Executive Summary (핵심 요약)

본 문서는 준호가 구축한 Blox + RiskLab 시뮬레이터(`2026-09-22_Blox_RiskLab_30m_01`)와 10월 7일 제기된 도메인 정합성 이슈(`Optimization 1007.pdf`), 그리고 10월 13일 최종 완성된 **Falcon-45 + Optimal Capped Pareto ($\text{Cap}=0.60, \alpha=1.0$)** ML 예측 모델을 하나로 통합한 **차세대 최적화 시뮬레이터의 아키텍처·수리모형·메타휴리스틱 해법 설계서이자 17종 실증 벤치마크 완료 보고서**입니다.

### 핵심 성과 요약 (611 의사결정 스텝, 100-GPU 코호트, 16,560개 실측 Job 리플레이 완료)
1. **작업 실패 손실(`JobFailLoss`) 100% 완전 제거 달성**:
   - 기존 위험도 미사용 베이스라인(`risk_blind_packed`: **`1,305s`**) 및 준호의 09-22 모델(`risk_prefer_packed` + E19: **`1,020s`**) 대비:
   - **해법 A (ML 모델만 Falcon-45 + Capped Pareto로 교체, `04_solA_falcon_prefer`)**만으로도 작업 실패 손실이 **`720s` (-44.8%)**로 감소하고 평균 JCT가 단축됨을 확인했습니다.
   - 여기에 **취약도 가중 다중작업 배치 수리모형(`05_solA_vuln_weighted_dp`)** 및 **Warm-Start 메타휴리스틱 배치 최적화(`06_solA_metaheuristic`)**를 결합한 결과, 리플레이 기간 중 발생한 **31건의 XID 에피소드 전부를 유휴(Idle) 또는 안전 시점 GPU로 회피시켜 작업 실패 손실 `0.0s` (-100.0% 감축, 실행 중 작업 중단 0건)**를 달성했습니다.
   - 특히 **Warm-Start 메타휴리스틱(`06_solA_metaheuristic`)**은 단일작업 순차 DP가 포착하지 못하는 다중 작업 간 교차 교환(2-Opt Swap + Simulated Annealing)을 통해 **누적 위험 노출(`RiskExp`)을 `3,197,932`에서 `830,788` (-74.0%)로, 취약도 가중 위험 노출(`VulnRiskExp`)을 `98.46B`에서 `24.23B` (-75.4%)**로 전 정책 중 최저 수준까지 낮추었습니다.
2. **선점 오버헤드(`PreemptCost`) 25.6% 감축 및 평균/꼬리 대기시간 대폭 단축 (`08_solA_full_co_opt`)**:
   - 시뮬레이터 전체 낭비의 99% 이상을 차지하던 LAS 무차별 선점 폭풍(`2,880,000s` = 800 GPU-hours)을 제어하기 위해 **비용-편익 선점 가드(Cost-Benefit Preemption Guard) + Best-Fit 희생양 선택**을 결합한 통합 정책(`full_co_optimized`)을 구현했습니다.
   - 그 결과 **스케줄링 선점 오버헤드를 `2,880,000s`에서 `2,144,160s`로 `-25.6%` (`735,840 GPU-초` = `204.4 GPU-시간` 절감)** 감축하면서도, **작업 실패 손실을 `345s` (-73.6% vs Blind)**로 억제하고, **평균 큐 대기시간(`AvgWait`)을 `-734.5s` (`63,844.1s` $\to$ `63,109.7s`), P95 꼬리 대기시간(`P95Wait`)을 `-22,202.5s` (`-6.17시간`, `-10.8%`), 평균 작업 완료시간(`AvgJCT`)을 `-930.4s` (`51,458.1s` $\to$ `50,527.7s`, `-1.81%`)** 단축하는 파레토 우위(Pareto Dominance)를 달성했습니다.
3. **해법 A와 해법 B의 양방향 구현 및 비교 완료**:
   - **해법 A (ML 재학습 없이 Branch 1 실시간 이상징후 확률 + Branch 2 만성 이력 확률 이중 피드 및 작업 취약도 연동)**와 **해법 B (시뮬레이터 내부 XID 43 소프트 리셋 vs XID 31 하드웨어 격리 이원화 및 혼합 시나리오/민감도 $\rho_{43} \in \{0.5, 1.0\}$ 분석)**를 모두 구현하고 17종 실험(Track 1~3)으로 완벽히 비교 검증했습니다.

### 2.1 준호의 기존 파이프라인(`BLOX_260922.pdf`) 경과 및 한계점

2. **인과성 리플레이 엔진 정립 (`시뮬레이터 계획서.pdf`, `Blox 기반 파이프라인 - 준호.pdf`, `BLOX_260922.pdf`)**:
   - `2026-09-22_Blox_RiskLab_30m_01`에서 **인과성 보장(Causal) 30분 결정 그리드(611 스텝, 2023-08-07 ~ 2023-08-20)**, **100-GPU 코호트(15개 서버)**, **실제 클러스터 트레이스(`job_trace.parquet`, 16,560개 Job)**, 그리고 **5대 손실 원장(`LossLedger`)**을 구축했습니다.
   - 그러나 당시 실험 결과에서 세 가지 구조적 병목이 발생했습니다:
     - **병목 ① (Hard Masking의 기아 현상)**: `risk_mask_packed`에서 99% 재현율 임계값($\tau = 0.002975$)을 하드 필터로 적용하자, 가용 GPU가 임계값에 걸려 **16,560개 작업 중 단 1개도 완료되지 못하는(`Completed = 0`, 100% Starvation)** 치명적 문제가 발생했습니다.
     - **병목 ② (단일 작업 순차 Greedy DP의 한계)**: `risk_prefer_packed`는 한 번에 작업 하나씩만 보고 서버 내 GPU 부분집합을 고르는 순차 탐욕(Single-Job Greedy) 방식이었습니다. 또한 작업의 크기($g_j$, Gang-Scheduling 폭)나 잔여 실행시간($r_j$)을 전혀 고려하지 않고, 1-GPU 단기 작업이든 8-GPU 장기 분산 학습 작업이든 똑같은 가중치로 취급했습니다.
     - **병목 ③ (과도한 선점 오버헤드 방치)**: Blox의 `Las`(Least Attained Service) 스케줄러가 매 300초마다 서비스 시간이 아주 조금만 적은 작업이 들어와도 실행 중인 대형 작업을 무차별 선점(Preemption)하여, 시뮬레이션 전체에서 **선점 오버헤드(`2,880,000 GPU-s`)가 장애 손실(`1,020 GPU-s`)의 2,800배**에 달했습니다.

### 2.2 `Optimization 1007.pdf`의 도메인 비판과 워크로드 실증 분석
`Optimization 1007.pdf`에서는 (1) NVIDIA 공식 문서상 **XID 31(MMU Fault)은 하드웨어/드라이버 수준의 결함**인 반면 **XID 43(Stopped Processing)은 사용자 앱/메모리 크래시 성격이 강해 두 코드를 시뮬레이터에서 똑같이 수 시간짜리 하드웨어 노드 다운타임으로 처리하는 것은 과도한 가정**이라는 점과, (2) 1-GPU 작업이 많아 체크포인트 손실 감축 폭이 작다는 우려를 제기했습니다.

이에 대해 실제 시뮬레이터 입력 데이터(`job_trace.parquet` 16,560개 작업 및 `failure_tape.parquet` 31개 에피소드)를 정밀 전수 분석한 결과, 다음의 핵심 근거를 발견했습니다:

> **핵심 인사이트 (Why Vulnerability-Weighted Metaheuristic Works)**:
> 작업 개수 기준으로는 1-GPU 작업이 75%이지만, **실제 GPU 시간을 소비하는 비중(GPU-Hours)은 8-GPU 이상 대형 Gang-Job이 84.2%를 차지하며, 상위 10% 장기 작업이 전체 연산량의 91.90%를 차지**합니다. 특히 Gang-Scheduling 특성상 8-GPU 작업은 할당된 8개 GPU 중 **단 1개에서만 XID 에러가 발생해도 8개 GPU 전체 작업이 즉시 중단**됩니다! 따라서 1-GPU 단기 작업을 저위험 GPU에 먼저 배정해 버리던 기존 단일작업 탐욕(Greedy) 방식을 폐기하고, **작업 취약도($V_j$) 가중 다중작업 동시 배치 최적화(Batch Co-Optimization)**를 도입하면 대형·장기 작업을 위험 노드로부터 완벽히 보호할 수 있습니다.

## 3. XID 31/43 통합 ML 모델과 시뮬레이터 연동을 위한 양대 해법 (해법 A & 해법 B)

사용자 요청에 따라, ML 모델을 재학습하지 않고도 도메인 정합성과 최적화 성능을 동시에 확보하는 **해법 A**와 **해법 B**를 모두 시뮬레이터(`blox-risklab/risklab/`)에 구현하고 비교 실험을 수행했습니다.

```
┌───────────────────────────────────────────────────────────────────────────────────┐
│        Falcon-45 + Optimal Capped Pareto (Cap=0.60, α=1.0) ML Engine              │
│   • Branch 1 (p_i^(B1)): 45개 텔레메트리 피처 (온도/전력/활용률 급변·이탈)          │
│   • Branch 2 (p_i^(B2)): 만성 장애 이력 (최근 30일 XID 빈도·재발 간격)              │
│   • Fused Risk (p_i^(fuse)): λ_i · p_i^(B1) + (1 - λ_i) · p_i^(B2)                │
└───────────────────────┬───────────────────────────────────────┬───────────────────┘
                        │                                       │
                        ▼                                       ▼
┌───────────────────────────────────────────┐   ┌───────────────────────────────────┐
│ [해법 A] 스케줄링 의사결정 계층 고도화      │   │ [해법 B] 장애 리플레이 충격량 계층  │
│  1. Dual-Branch 실효 위험도 산출           │   │  1. XID 코드 파싱 (_parse_xid)    │
│     r_i^eff = p_i^fuse + η·p_i^B1·I(p^B2) │   │  2. XID 31 (Hardware Fault):      │
│  2. 작업 취약도 (Vulnerability V_j) 가중   │   │     • 작업 중단 + 장기 노드 격리   │
│  3. 예산 제약형 Top-K 동적 격리 (기아 방지)│   │  3. XID 43 (App/Soft Reset):      │
│  4. 메타휴리스틱 배치 + 선점 가드          │   │     • 확률 ρ_43 중단 + 60s 리셋   │
└───────────────────────┬───────────────────┘   └───────────────┬───────────────────┘
                        └───────────────────┬───────────────────┘
                                            ▼
┌───────────────────────────────────────────────────────────────────────────────────┐
│             Extended 7-Metric LossLedger & Pareto Performance Evaluator           │
└───────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 해법 A: Dual-Branch 피드 분해 + 작업 취약도($V_j$) 연동 + 슬랙 기반 Top-$K$ 동적 격리
1. **ML 재학습 없는 Dual-Branch 피드 직접 주입 ([`feeds.py`](file:///C:/Users/jehan/Desktop/IISE%20%EC%BB%A8%ED%8D%BC%EB%9F%B0%EC%8A%A4/ISEE_Project/experiments/2026-09-22_Blox_RiskLab_30m_01/blox-risklab/risklab/feeds.py))**:
   - 우리의 최종 ML 모델(`UnifiedADSTPipeline`)은 이미 추론 시점에 **Branch 1 확률($p_{i,t}^{(B1)}$, 45개 물리적 텔레메트리 피처 기반)**, **Branch 2 확률($p_{i,t}^{(B2)}$, 과거 XID 반복 빈도 기반)**, 그리고 **Capped Pareto 결합 확률($p_{i,t}^{(\text{fuse})}$)** 세 가지를 모두 생성합니다.
   - 시뮬레이터의 `CausalProbabilityProvider.branch_snapshot(t)`이 세 확률을 동시에 읽어들이도록 확장했습니다.
   - 만성 장애 이력이 있는 GPU($p_{i,t}^{(B2)} > P_{75}$)에서 물리적 텔레메트리 이상징후($p_{i,t}^{(B1)}$)까지 동반 상승할 경우 복합 시너지 페널티를 부여하는 **실효 위험도(Effective GPU Risk)**를 정의했습니다:
     $$r_{i,t}^{\text{eff}} = p_{i,t}^{(\text{fuse})} + \eta \cdot p_{i,t}^{(B1)} \cdot \mathbb{I}\!\left(p_{i,t}^{(B2)} > Q_{0.75}(p_t^{(B2)})\right) \quad (\eta = 0.25)$$
2. **예산 제약형(Slack-Aware) Top-$K$ 동적 격리 ([`replay_engine.py`](file:///C:/Users/jehan/Desktop/IISE%20%EC%BB%A8%ED%8D%BC%EB%9F%B0%EC%8A%A4/ISEE_Project/experiments/2026-09-22_Blox_RiskLab_30m_01/blox-risklab/risklab/replay_engine.py))**:
   - 준호의 고정 임계값 마스킹(`risk_mask_packed`)이 일으킨 100% 기아 현상을 해결하기 위해, 현재 라운드에서 **할당 대기 중인 작업들의 총 요구 GPU 수($D_{\text{req}}$)를 먼저 계산한 뒤, 클러스터 잉여 유휴 GPU 슬랙($S_{\text{slack}} = \max(0, |\mathcal{G}_{\text{free}}| - D_{\text{req}})$) 및 최대 예산 $B_{\max}$ 범위 내에서만** 최상위 고위험 유휴 GPU를 일시 격리합니다. 작업 수요가 가용 GPU를 초과할 때는 격리 수를 자동으로 0으로 줄여 **기아(Starvation)를 수학적으로 0%로 보장**합니다.

## 4. 차세대 수리모형(Mathematical Formulation) 및 최적화 해법 설계

### 4.1 작업 취약도(Job Vulnerability Weight, $V_j$) 정의
시각 $t$에 배치할 작업 $j \in \mathcal{J}_t$의 요구 GPU 수를 $g_j$, 잔여 실행시간을 $r_j$, 현 시점까지의 무체크포인트 진행시간을 $u_j$, 체크포인트 주기를 $I_{\text{ckpt}} (= 300\text{s})$, 장애 복구 재시작 지연을 $D_{\text{rec}} (= 300\text{s})$, 스케줄러 우선순위 가중치를 $\omega_j$라 할 때, 작업 $j$가 배치 윈도우 $\Delta H = 1800\text{s}$ 동안 직면하는 **잠재 장애 손실 취약도 $V_j$**를 다음과 같이 정의합니다 ([`placement_policy.py`](file:///C:/Users/jehan/Desktop/IISE%20%EC%BB%A8%ED%8D%BC%EB%9F%B0%EC%8A%A4/ISEE_Project/experiments/2026-09-22_Blox_RiskLab_30m_01/blox-risklab/risklab/placement_policy.py)):

$$V_j = \omega_j \cdot g_j^{1.25} \cdot \left(D_{\text{rec}} + \min(I_{\text{ckpt}}, u_j + \Delta H)\right) \cdot \left(1 + \frac{\min(r_j, 4\Delta H)}{\Delta H}\right)$$

- **물리적 의미**:
  1. $g_j^{1.25}$: $g_j$개 GPU가 동시에 묶여 돌아가는 Gang-Job은 어느 한 GPU만 고장 나도 $g_j$개 전체가 중단되고 재시작 시 $g_j \times D_{\text{rec}}$만큼의 클러스터 GPU-초를 낭비하므로 초선형(Super-linear) 보호 가중치를 부여합니다.
  2. $\left(1 + \frac{\min(r_j, 4\Delta H)}{\Delta H}\right)$: 앞으로 오랫동안 GPU에 상주할 장기 작업일수록 향후 30분~2시간 내 장애 에피소드와 조우할 노출 시간이 길어지므로 저위험 서버에 우선 배치합니다.

### 4.2 다중 작업 동시 배치 및 선점 제어 수리모형 (BILP)
매 스케줄링 라운드 $t$에서 승인된 배치 대상 작업 집합 $\mathcal{J}_t$와 가용 GPU 집합 $\mathcal{G}_t$에 대하여, 이진 결정변수 $x_{j,i} \in \{0, 1\}$ (작업 $j$에 GPU $i$ 할당 여부)와 서버 사용 변수 $y_{j,s} \in \{0, 1\}$ (작업 $j$가 서버 $s$를 사용하는지 여부)를 최적화합니다:

$$\min_{x, y} \quad \mathcal{Z}(x, y) = \underbrace{\alpha_{\text{pack}} \sum_{j \in \mathcal{J}_t} \sum_{s \in \mathcal{S}} y_{j,s}}_{\text{서버 단편화(Fragmentation) 최소화}} + \underbrace{\beta_{\text{risk}} \sum_{j \in \mathcal{J}_t} V_j \sum_{i \in \mathcal{G}_t} r_{i,t}^{\text{eff}} \, x_{j,i}}_{\text{취약도 가중 장애 위험 노출 최소화}} + \underbrace{\gamma_{\text{hot}} \sum_{j \in \mathcal{J}_t} V_j \max_{i: x_{j,i}=1} r_{i,t}^{\text{eff}}}_{\text{Gang-Job 내 최악 고위험 GPU 병목 회피}}$$

**제약조건 (Constraints)**:
1. **GPU 용량 제약**: $\sum_{i \in \mathcal{G}_t} x_{j,i} = g_j \quad (\forall j \in \mathcal{J}_t)$
2. **GPU 독점 할당 제약**: $\sum_{j \in \mathcal{J}_t} x_{j,i} \le 1 \quad (\forall i \in \mathcal{G}_t)$
3. **서버 패킹 연결 제약**: $x_{j,i} \le y_{j,s(i)} \quad (\forall j \in \mathcal{J}_t, \forall i \in \mathcal{G}_t)$
4. **비용-편익 선점 가드 제약 (Cost-Benefit Preemption Guard)**:
   대기 작업 $j$가 실행 중인 작업 집합 $\mathcal{P}$를 선점하려면 아래 세 조건을 모두 만족해야 함:
   - **(a) 서비스 시간 우위 마진**: $\text{AttainedService}(j) + \Delta_{\text{margin}} < \min_{p \in \mathcal{P}} \text{AttainedService}(p)$ ($\Delta_{\text{margin}} = 300\text{s}$ — 불과 몇 초 차이로 발생하는 무의미한 핑퐁 선점 차단)
   - **(b) 완료 임박 작업 보호 (Tail Protection)**: 선점 대상 작업 $p \in \mathcal{P}$의 잔여 완료시간이 $r_p \le 180\text{s}$ 이하이면 선점 금지 (곧 끝날 작업을 죽여서 `240s` 선점 페널티를 무는 역설 방지)
   - **(c) Best-Fit 희생양 선택**: 선점이 불가피할 때는 가장 서비스 시간이 많이 쌓인 소수 작업부터 최소 서버 단편화 및 최저 위험 노출 점수로 선택.
